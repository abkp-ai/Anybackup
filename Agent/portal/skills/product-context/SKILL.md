# 产品上下文

在 `当前仓库` 工作时，需要把当前实现、原型和需求三类资料结合起来，再做产品或 UI 实现决策。

## 三个项目的角色

1. 当前实现：`当前仓库`
2. 原型项目：`../../../ui-prototype`
3. 需求项目：`../../../aa-feat`

- 将 `../../../aa-feat` 视为产品和需求的事实来源。
- 将 `../../../ui-prototype` 视为原型和交互参考。
- 将 `当前仓库` 视为实现目标。
- 除非用户明确要求，否则只编辑 `当前仓库`。

## 需求阅读顺序

做功能或页面工作时，先读取最具体、最相关的需求文件：

1. `../../../aa-feat/README.md`
2. `../../../aa-feat/docs` 下的版本和 MVP 文档
3. `../../../aa-feat/docs` 下的功能规格文档
4. 只有当任务依赖技术行为时，再读取 `../../../aa-feat/docs` 下的架构或服务设计文档

当任务提到模块、页面、流程或关键词时，在 `../../../aa-feat/docs` 下做定向文件列表和搜索。很多需求文件名是中文或本地化命名，不要依赖本技能里硬编码的文件名，应该从文件系统发现准确路径。

## 原型阅读顺序

做 UI 或交互工作时，在读取相关需求后检查原型：

1. `../../../ui-prototype/src/App.tsx`
2. `../../../ui-prototype/src/pages` 下相关页面
3. `../../../ui-prototype/src/components` 下相关组件
4. `../../../ui-prototype/src/data` 下 mock 数据
5. `../../../ui-prototype/docs` 下原型辅助文档

使用原型理解布局、文案、用户流程、状态示例和视觉优先级。不要盲目复制原型代码；如果当前项目已有更干净或更一致的模式，应优先沿用当前项目模式。

## 实施流程

1. 读取相关需求文件。
2. 检查匹配的原型文件。
3. 检查 `../../src` 中的当前实现。
4. 对比需求意图、原型行为和当前代码。
5. 尽量保留 `web_app_agent` 已有实现模式。
6. 如果需求和原型冲突，明确指出冲突；默认以需求项目为准，除非用户另有说明。
7. 将改动限制在用户请求的功能、页面或行为范围内。

## 当前实现定位

- `../../src/app/router.tsx`：路由定义和受保护布局。
- `../../src/pages`：路由级页面。
- `../../src/components`：可复用 UI 和功能组件。
- `../../src/store`：Zustand 状态。
- `../../src/lib`：业务逻辑和工具函数。
- `../../src/types`：共享 TypeScript 类型。

## 决策规则

- 产品范围不清时，先查需求项目；不要从当前代码或原型猜测长期范围。
- 交互细节不清时，查原型；如果原型比需求更具体，说明这是从原型推断出的实现细节。
- 当前实现和原型不一致时，优先评估当前项目已有架构和组件边界，再决定是否迁移原型行为。
- 用户明确指定“按原型”时，原型交互优先；仍需避免引入 V1 范围外功能。
- 用户明确指定“只做入口”“删除非 V1 功能”时，不保留审批、执行、CLI、RBAC 或后续规划功能的 UI。
